一、项目定位与目标

1.1 一句话定义

家长记录宝宝的每一次成长与每一餐饮食，系统把数据变成看得懂的生长曲线、营养分析和"现在能吃什么"的直接答案。

成长宝是一款面向 0-3 岁婴幼儿父母及主要照料者的辅食与成长管理平台，以响应式 Web 应用形态交付——浏览器即用，手机、平板、电脑体验一致，无需安装。它不做"育儿内容门户"，而是围绕自家宝宝的数据做闭环：记录 → 分析 → 推荐 → 指导。所有分析与推荐都从"宝宝档案 + 记录数据"推导，而不是让用户填问卷。

1.2 背景：四个真实问题

#问题具体表现
1知识获取碎片化辅食添加知识散落在社交平台、短视频与口口相传中，质量参差不齐，新手父母难以辨别哪些适用自家宝宝
2记录工具分散成长数据、饮食情况、疫苗体检分散在多个 App 甚至纸笔记录中，无法形成完整的成长画像
3缺乏个性化指导多数食谱类产品只提供"通用内容"，不结合宝宝月龄、过敏史、饮食偏好给针对性推荐；看到"6 个月能吃什么"的答案，还要自己再判断过不过敏、合不合适
4喂养焦虑普遍奶量够不够、辅食添加顺序对不对、发育是否达标，是新手父母最高频的疑问，却没有一站式答案

这四点决定了产品的技术路线：个性化交给数据与规则，正确性交给确定性代码——过敏规避、月龄筛选、参考线判断全部落在服务层与 SQL 层，不依赖前端软过滤，也不输出模糊的"仅供参考"。

1.3 目标与非目标

目标衡量方式
降低记录门槛一次录入同时服务生长曲线、营养分析、辅食推荐三处，不做重复填写
分析可解释生长曲线叠加 WHO 2006 标准分位参考线（P3 / P15 / P50 / P85 / P97，0-24 月龄男女分开），并明确标注"参考"而非"诊断"
推荐可信过敏食材在 SQL 层硬过滤（WHERE 下推），而非前端软过滤；规避结果有明确提示
多孩友好一个账号管理多个宝宝档案，所有数据按档案归属做权限隔离
结果可验证117 个自动化用例覆盖单元 / 集成 / 契约 / 迁移 / 限流 / E2E，接口行为有测试锁定

非目标（本期明确不做）：母婴社区与 UGC 内容平台；母婴电商与带货；医疗诊断（WHO 参考数据明确标注不用于临床评估，异常区间建议就医）；小程序 / 原生 App 端。

1.4 目标用户

用户类型核心诉求对应设计
新手父母（0-1 岁为主）喂养高频疑问、辅食添加顺序分月龄喂养指南 + FAQ + 按月龄推荐
二胎 / 多孩家庭一个账号管理多个宝宝多档案切换、数据按宝宝归属隔离
全职照料者（含祖辈）操作简单、结论直白看得懂响应式手机适配、自绘大字号曲线、直白的区间提示

4.5 模块依赖关系

依赖关系的三条硬规则：

  • 单向依赖：路由 → 服务 → 模型 / 数据。服务之间不反向调用路由，避免循环依赖。
  • 服务层不触 HTTP：全部业务逻辑在服务层以函数形式实现（单入单出），路由层只做参数校验与编排，因此服务层可被多个端点复用，也可独立单测。
  • 前端组件不直接发请求：组件只消费 store 状态，请求一律经 store action 调用 api 模块，错误处理集中在 Axios 拦截器。

七、关键设计原则

原则落地方式
个性化来自数据，不来自问卷月龄由出生日期推算，过敏来自档案登记，偏好来自收藏与记录——不要求用户填写任何偏好问卷
过滤逻辑下推数据库月龄、食材、营养、关键词、过敏规避全部条件下推 SQL WHERE，避免全表加载后内存过滤，数据量增长不劣化
跨库行为一致生产 MySQL / 测试 SQLite 双兼容：不用数据库专有 JSON 函数，改用统一序列化器 + 文本匹配方案，测试结论对生产有效
参考不诊断WHO 参考线数据在代码注释与接口文档中明确标注"用于绘图参考，不用于临床诊断"，异常区间引导就医而非给出医疗结论
契约先行Pydantic 响应模型 + 统一响应体 {code, message, data} + 统一业务错误码表；test_contract.py 契约测试锁定接口行为，前端 TS 类型与后端模型对应
全链路可测117 个用例分层组织：单元（月龄计算等纯函数）、集成（各模块 API）、契约、迁移、限流、E2E 全流程（注册 → 建档 → 记录 → 推荐）
